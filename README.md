# Delta Lab

Delta Lab compares two Python source files using actual execution, while NVIDIA Nemotron proposes input cases from the diff. It is a local developer tool for functions whose arguments and results are JSON-compatible. Differences are observations, not automatic proof of a defect. Review the intended behavior before adopting an exported test.

## Setup

Requires Python 3.10+, `jsonschema`, Docker Desktop running with Linux containers, and the local `python:3.11-alpine` image. Install with `python -m pip install jsonschema pytest`, then run `docker pull python:3.11-alpine`. Set `NEBIUS_API_KEY`; a `.env` or `.env.txt` in the parent project folder is also read. Run `python server.py` from this directory and open http://127.0.0.1:8000. `PORT`, `HOST`, `DELTA_IMAGE` and `NEBIUS_MODEL` can override defaults. The server enforces a localhost-only bind; it is not a hosted multi-user service.

If Docker or the image is unavailable, analysis fails closed. Nothing executes on the host as a fallback. The sandbox has no network, a read-only filesystem, a small temporary filesystem, a non-root user, dropped Linux capabilities, Docker's default seccomp policy, and memory, CPU, PID, output and wall-time limits. Docker is not a hardened multi-tenant security boundary; use only trusted code and a dedicated machine for stronger isolation. Imported packages must already exist inside the sandbox image. Source and schema are sent to Nebius when model suggestions are enabled; never submit confidential code without authorization.

## Inputs and observations

Schema references and regex patterns are unsupported. Inputs are limited to 12 nesting levels, 100 entries per array or object, and 10,000 characters per string to bound coordinator work. Each input is a JSON object such as `{"args":[1],"kwargs":{}}`, validated against the supplied JSON Schema. The named function must exist in both self-contained files. Standard-library imports supported by the image work; external package dependencies require a custom image. Model proposals are validated, deduplicated, and never treated as results. The actual old and new functions run in separate fresh containers for each evaluation. JSON return values are compared. Exception comparisons use qualified class and base names, a 1,000-character preview, and the full message length and SHA-256; local class modules are normalized for export. Failed loading, unsupported return types, sandbox failures and timeouts stop analysis rather than become claimed behavioral differences. Comparison uses JSON serialization, so tuples become arrays. Time, randomness, process-wide side effects, platform differences and nondeterministic code can still cause differences; this tool cannot guarantee that functions are pure or deterministic.

Analysis has a 120-second overall deadline and a budget of 30 completed comparisons; a run interrupted after at least one result is marked incomplete with a reason. The shrinker performs up to eight schema-valid, locally simplifying attempts for a differing input. Its trace records each actual comparison; this is not guaranteed globally minimal. Runs may be slow because each comparison starts two containers. Downloaded pytest tests assert the observed old behavior against a module selected with `DELTA_TARGET_MODULE`. Example: `set DELTA_TARGET_MODULE=my_module` on Windows, then `python -m pytest test_delta_regression.py`. Review the expectation, import path and dependency context before adopting. Exported tests execute the selected module in your normal test environment; pytest can reuse module state across parameter cases, whereas each sandbox comparison starts fresh.

## Example and verification

The CPython example contains unmodified `Lib/urllib/parse.py` from parent commit `bf124244f0595fb3b4f969a31644b7d110de41ef` and commit `8a595744e696a0fb92dccc5d4e45da41571270a1` for [bpo-43882](https://bugs.python.org/issue43882). The accompanying candidate is derived from the upstream test. Python's license is included with the fixture. No result is precomputed: the app must execute each side before showing a comparison. The model may fail, propose invalid or duplicate cases, or miss the behavior; user-supplied cases continue when model generation fails.

Run `python -m pytest test_server.py -q`. The Docker integration test is skipped if the engine/image is unavailable. A complete HTTP analysis was verified here using the experimental WSL runner, a live Nemotron request, and the upstream case: the old result had an empty scheme and netloc, while the new result recognized `http` and `www.python.org`. The runner also shrank that input. The generated pytest test was then run in an isolated WSL sandbox against each pinned source: it passed on the old revision and failed on the new revision, as expected for its recorded baseline. Docker execution has not been verified here because its engine did not start. Rerun the integration test and the example after setup; successful unit tests with mocked execution do not establish sandbox behavior.
# Delta Lab sandbox and output integrity

Delta Lab executes submitted source and is intended **only for trusted, non-adversarial code**. Both implementations share an interpreter with the function under test, so code can tamper with modules, runtime state, file descriptors, or the output protocol; returned results are not tamper-proof. Capturing output and serialization references prevents a few accidental or simple monkeypatches, not malicious interference. Review code before execution.


## Experimental WSL runner (Windows)

Docker remains the default. To opt in, install bubblewrap in the Ubuntu WSL distribution and ensure Ubuntu x86_64 has `/usr/bin/python3.12` and its standard libraries. In PowerShell, set `$env:DELTA_RUNNER="wsl"` before starting the server. If bubblewrap is not on the WSL PATH, set `$env:DELTA_WSL_BWRAP="/absolute/linux/path/to/bwrap"`. Set `$env:DELTA_WSL_DISTRO` if the distribution is not `Ubuntu`. The server probes the selected sandbox before every analysis and fails closed on errors. There is no automatic fallback between runners.

The WSL launcher creates separate user, network, PID, mount, IPC and UTS namespaces with bubblewrap; binds only Python's executable, standard library and selected runtime libraries read-only; and does not mount the project, home directories, Windows drives or secrets. It clears the environment and drops capabilities. It also applies a wall timeout, output limits, and Linux per-process resource limits. These limits are **not aggregate cgroup quotas**: CPU and address-space limits apply per process and the process-count limit is shared by the WSL user. The WSL option is experimental, intended only for trusted non-adversarial code, and is not a VM or production multi-tenant boundary. See the Docker requirements and protocol limitations above.
